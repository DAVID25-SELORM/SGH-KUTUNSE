# StormerHost Phase 1 deployment

This runbook prepares the public Satellite General Hospital website for StormerHost. It does not authorize deployment, DNS changes, SSL changes, or edits to the Ark Medical Centre website.

## Deployment decision

- GitHub source: `https://github.com/DAVID25-SELORM/SGH-KUTUNSE.git`
- Production branch after review: `main`
- Node.js: `22`
- Package manager: npm, using the committed `package-lock.json`
- Application mode: `Production`
- Application root: `sgh-kutunse` relative to the cPanel account home directory
- Application URL: `https://satellitegeneralhospital.com/`
- Startup file: `app.js`
- Runtime: Next.js standalone server generated by `next build`

Standalone output is preferred because cPanel/Passenger expects a JavaScript startup file. Next.js generates the actual minimal server at `.next/standalone/server.js`; the repository's `app.js` only loads that generated server. There is no custom Express server. The generated server respects the `PORT` supplied by the hosting process.

Build the application on StormerHost's Linux environment. Do not upload a Windows-generated `.next/standalone` directory because native runtime dependencies can be platform-specific.

## 1. Preflight with StormerHost

Before uploading anything, confirm that this cPanel account provides:

1. Node.js 22 in **Node.js Web Applications** or **Application Manager**.
2. A production application mapped to the root of `satellitegeneralhospital.com`.
3. Terminal/SSH or equivalent cPanel actions for `npm ci`, `npm run build`, and `npm run stage:stormerhost`.
4. Passenger or the hosting process injecting `PORT`. Do not manually choose or hardcode a port.
5. Enough memory and execution time for a Next.js 16 production build.

Do not continue if the interface only supports static sites or if Node.js 22 is unavailable.

## 2. Upload the source

Preferred method: deploy the reviewed Git commit into `~/sgh-kutunse` using cPanel Git Version Control or a private-repository deployment credential.

For this cPanel account, Git Version Control clones the repository separately and uses the committed `.cpanel.yml` to deploy into `/home2/arkmedic/sgh-kutunse`. After updating the repository to the desired `main` commit, use **Deploy HEAD Commit**. The deployment tasks copy source without Git metadata or local build/dependency folders, activate the SGH Node 22 environment, run a clean dependency install, lint, build, stage the standalone runtime, and signal Passenger to restart this application.

Review the cPanel deployment log after every deployment. A failed task must stop acceptance testing; do not assume later steps completed.

Alternative: upload the prepared source archive and extract it into `~/sgh-kutunse`.

The application root must not be `public_html` and must not be the Ark Medical Centre application directory. Do not copy this application into the Ark website.

The source deployment must include `app`, `components`, `data`, `lib`, `media`, `public`, `scripts`, `types`, `app.js`, configuration files, `package.json`, and `package-lock.json`.

It must exclude `.git`, local `.next`, `node_modules`, `.npm-cache`, `.env*` other than `.env.example`, Firebase deployment caches, logs, and local temporary files.

## 3. Create/configure the cPanel application

Enter these values in **Node.js Web Applications**:

| cPanel field | Value |
| --- | --- |
| Node.js version | `22` |
| Application mode | `Production` |
| Application root | `sgh-kutunse` |
| Application URL/domain | `satellitegeneralhospital.com` |
| URL path | `/` or blank when cPanel represents the domain root with a blank path |
| Application startup file | `app.js` |

Do not select `arkmedicalgh.com`. Do not use an Ark Medical `public_html` directory as the application root.

If cPanel creates the application before the build exists, it may initially report a startup error. Complete the install/build/stage steps below, then restart the application.

## 4. Environment variables

### Required runtime values

- `NODE_ENV=production` — normally set by **Application mode: Production**. Confirm it is present.
- `PORT` — must be supplied automatically by cPanel/Passenger. Do not set a fixed value in cPanel or source code.

There are no required application secrets in Phase 1.

### Optional Firebase Analytics values

Analytics is optional. The website renders normally when these are absent. To retain Firebase Analytics, enter the complete public browser configuration as cPanel environment variables:

- `NEXT_PUBLIC_FIREBASE_API_KEY`
- `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`
- `NEXT_PUBLIC_FIREBASE_PROJECT_ID`
- `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET`
- `NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID`
- `NEXT_PUBLIC_FIREBASE_APP_ID`
- `NEXT_PUBLIC_FIREBASE_MEASUREMENT_ID`

These are public Firebase web-app identifiers, not Firebase Admin credentials. Never add a service-account key, Firebase Admin private key, database credential, or other private secret to the repository or browser variables.

### Development only

No development-only variable is required. Local `.env.local` files must not be uploaded.

## 5. Install, build, and stage on Linux

Open cPanel Terminal/SSH or use the equivalent commands exposed by the Node.js application interface:

```bash
cd ~/sgh-kutunse
node --version
npm --version
npm ci
npm run lint
npm run build
npm run stage:stormerhost
```

`node --version` must report a Node 22 release. If cPanel requires activation of its Node.js 22 environment first, use the activation command displayed by that cPanel application; do not guess a system-wide Node path.

The build produces `.next/standalone/server.js`. The staging command copies `public/` and `.next/static/` into the standalone runtime, as required by Next.js.

## 6. Restart

Use the application's **Restart** action in cPanel after every successful build and stage operation. If the interface exposes Passenger restart files instead, use only the mechanism documented by StormerHost for this application. Do not restart or reconfigure the Ark Medical application.

## 7. Domain and canonical-host verification

After restart, verify:

```text
https://satellitegeneralhospital.com/
```

The application contains a permanent host redirect from `www.satellitegeneralhospital.com` to `satellitegeneralhospital.com`, preserving the path. DNS is managed separately and must not be changed during this deployment procedure.

## 8. SSL

SSL terminates at cPanel/Apache and is not implemented in Next.js.

1. Confirm cPanel AutoSSL has issued a certificate covering both `satellitegeneralhospital.com` and `www.satellitegeneralhospital.com`.
2. Open both HTTPS hosts in a browser and inspect the certificate names and expiry.
3. Only after HTTPS works without warnings, enable cPanel's **Force HTTPS Redirect** for the SGH domain.
4. Recheck the root page and at least one nested route over HTTPS.

Do not enable forced HTTPS before certificate issuance succeeds.

## 9. Production acceptance checklist

Verify HTTP `200` responses and visible layouts for:

- `/`
- `/about`
- `/appointments`
- `/contact`
- `/corporate-wellness`
- `/directions`
- `/doctors`
- `/insurance`
- `/patient-resources`
- `/privacy`
- `/screening`
- `/services`
- `/telemedicine`
- `/terms`
- `/health`
- one `/doctors/[slug]` route
- one `/services/[slug]` route
- one `/health/[slug]` route
- `/robots.txt`
- `/sitemap.xml`

Also verify:

- logo, hero, service, article, directions, and screening images;
- mobile header and bottom actions;
- canonical metadata uses `https://satellitegeneralhospital.com`;
- the `www` host redirects to the preferred host;
- appointment, contact, insurance, and corporate forms cannot claim success and display both hospital phone numbers;
- telemedicine directs visitors to call rather than claiming an online request was submitted;
- API POST routes return `503` without echoing or logging personal data;
- the Patient Portal is labelled **Coming Soon**;
- no admin route is present.

## 10. Rollback

Before each future release, record the currently deployed Git commit.

To roll back:

1. Check out the last known-good commit in `~/sgh-kutunse` using Git, or restore its reviewed source archive.
2. Run `npm ci` if dependencies changed.
3. Run `npm run build`.
4. Run `npm run stage:stormerhost`.
5. Restart only the SGH Node.js application.
6. Repeat the route and SSL smoke tests.

Do not roll back by editing generated `.next` files or individual production source files through File Manager.

## 11. Future updates

Use this workflow:

```text
Local/Codex change
  -> lint and production build
  -> Git commit
  -> reviewed push to GitHub main
  -> update ~/sgh-kutunse to that commit
  -> npm ci when lockfile changes
  -> npm run build
  -> npm run stage:stormerhost
  -> restart the SGH Node.js application
  -> production smoke tests
```

Avoid direct production edits in cPanel File Manager except for emergency recovery. Reproduce and commit every emergency fix to Git immediately afterward so GitHub remains the source of truth.

## 12. Phase 1 limitations

- Public form submission is intentionally unavailable until durable storage and administrative workflows exist.
- Firebase Analytics is optional and inactive without the complete public web configuration.
- Doctors and health articles remain clearly labelled demo content.
- The Patient Portal is a Coming Soon page.
- Careers lists no vacancies and accepts no applications during Phase 1.
- No admin portal or persistent backend is included.
